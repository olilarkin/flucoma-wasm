# Fluid Corpus Manipulation: Command line interface

This repository hosts code for generating the command line executables and documentation resources for the Fluid Corpus Manipulation Project. Much of the actual code that does the exciting stuff lives in this repository's principal dependency,  the [Fluid Corpus Manipulation Library](https://github.com/flucoma/flucoma-core).

* A wrapper from our code that allows us to generate command-line executables from a generic class.
* Stubs for producing an executable for each 'client' in the Fluid Corpus Manipulation Library.
* CMake code for managing dependencies, building and packaging.
* A WebAssembly build of the same programs, published to npm as **`flucoma-wasm`** — see below.

---

# `flucoma-wasm` — the npm package

The same command-line programs, compiled to WebAssembly, so they run in Node,
in the browser and in Web Workers with no native binary and no install step.

This is not a reimplementation. The build (`scripts/build-wasm.sh`) reuses this
repository's own CMake and the same generated stubs the native executables are
built from, so the WebAssembly programs *are* the programs — same algorithms,
same option grammar, same results.

```bash
npm install flucoma-wasm
```

## Quick start

```js
import { Fluid, encodeWav, decodeWav } from 'flucoma-wasm';

const fluid = new Fluid();

// Where are the interesting moments? -> slice points, in samples
const points = await fluid.slice('fluid-noveltyslice', wavBytes, { threshold: 0.4 });

// What does it sound like? -> one channel per coefficient, one frame per hop
const mfcc = await fluid.analyse('fluid-mfcc', wavBytes, { numCoeffs: 13 });

// Pull it apart -> WAV bytes per output
const { harmonic, percussive } = await fluid.decompose('fluid-hpss', wavBytes);
```

Audio goes in as WAV/AIFF bytes, a decoded `{ sampleRate, channelData }`, or a
Web Audio `AudioBuffer`. Analysis comes back decoded; audio comes back as
32-bit float WAV bytes.

## What's bundled

24 programs, in four families. `fluid list` prints them, and
`fluid help <program>` describes any one of them in full.

| kind | programs |
| --- | --- |
| **slicer** — writes `indices` | `ampgate` `ampslice` `noveltyslice` `onsetslice` `transientslice` |
| **analyser** — writes `features` | `ampfeature` `chroma` `loudness` `melbands` `mfcc` `noveltyfeature` `onsetfeature` `pitch` `spectralshape` |
| **decomposer** — writes audio | `audiotransport` `hpss` `nmf` `nmfcross` `nmfseed` `sinefeature` `sines` `stft` `transients` |
| **stats** | `stats` |

## API

`Fluid` has one general method and three typed conveniences:

- **`run(program, argv, io)`** — raw command line, exactly as the native tools
  take it. The escape hatch: anything the programs accept works here.
- **`invoke(program, params)`** — a typed parameter object. Stages the input
  buffers, requests every output, decodes the results.
- **`slice` / `analyse` / `decompose`** — one-liners over `invoke` for the three
  common shapes.

Parameters are named as the toolkit declares them (`fftSettings`,
`minSliceLength`), matched case-insensitively, and enums accept the choice name:

```js
await fluid.slice('fluid-noveltyslice', wav, {
  algorithm: 'MFCC',          // instead of the index 1
  kernelSize: 11,
  fftSettings: [2048, 512, 2048],
});
```

Two details worth knowing:

- **Some options take more than one value.** `fftSettings` takes four (window,
  hop, FFT size, maximum FFT size) and the "runtime max" numbers take two. Pass
  as many as you care about; the rest are padded with `-1`, the toolkit's own
  "work it out" value.
- **Out-of-range values are rejected up front.** The programs don't range-check
  themselves — a `kernelSize` of 4 (declared `Min(3)`, `Odd()`) reads off the
  end of the WebAssembly heap and aborts the module, which is not recoverable.
  So `invoke` checks values against the declared constraints and throws a
  `RangeError` first. `run` skips the check if you need to get past it.

Every program, option, type, default and constraint lives in `src/catalog.js`,
generated by `scripts/harvest-catalog.mjs` from the built modules and the
flucoma-core headers — so it can't drift from what actually shipped.

## Command line

```bash
npx fluid noveltyslice -source in.wav -indices slices.csv -threshold 0.4
npx fluid mfcc         -source in.wav -features mfcc.csv  -numcoeffs 13 -1
npx fluid hpss         -source in.wav -harmonic h.wav -percussive p.wav

npx fluid list slicer        # what's available
npx fluid help mfcc          # parameters, defaults, ranges
npx fluid doctor             # check the modules load and run
```

Options pass straight through, so anything the native tools accept works. An
output whose filename ends in `.csv` is written as text rather than audio.

## Interoperability with cdp-wasm

[`cdp-wasm`](https://github.com/cdp-wasm-suite/cdp-wasm) brings the CDP suite to
the same runtime, and the two packages are built to be used together.

**They already share a data format.** Both decode audio to
`{ sampleRate, numChannels, length, channelData, bitDepth }` with planar
`Float32Array` channels, and both pass audio as 32-bit float WAV bytes. So the
output of one is directly the input of the other — no conversion, no adapter,
and no dependency between the packages:

```js
import { CDP } from 'cdp-wasm';
import { Fluid } from 'flucoma-wasm';

const cdp = new CDP();
const fluid = new Fluid();

const { bytes } = await cdp.process('modify', ['speed', '2', '$IN', '$OUT'], wav);
const points = await fluid.slice('fluid-noveltyslice', bytes);
```

**Where they complement each other is structure.** FluCoMa is good at finding
and describing the interesting moments; CDP is good at transforming audio.
`flucoma-wasm/interop` has the segment plumbing for that pipeline:

```js
import { mapSlices, describeSlices, cut, concat } from 'flucoma-wasm/interop';

// Slice with FluCoMa, transform each segment with CDP, reassemble
const out = await mapSlices(fluid, wav, async (segment, i) => {
  const { bytes } = await cdp.process(
    'modify', ['speed', String(1 + i * 0.1), '$IN', '$OUT'], segment);
  return bytes;                      // or return null to drop the segment
}, { program: 'fluid-transientslice', crossfade: 5 });

// Or describe each segment first, and let the descriptor drive the treatment
const slices = await describeSlices(fluid, wav, {
  analyser: 'fluid-pitch',
  summary: 'median',
});
slices.sort((a, b) => a.descriptors[0] - b.descriptors[0]);   // low to high
const sorted = concat(slices.map((s) => s.segment), { crossfade: 5 });
```

`mapSlices` takes a plain callback rather than a CDP handle, so it works with
cdp-wasm, with another FluCoMa call, with Web Audio, or with anything else that
maps WAV bytes to WAV bytes. Neither package depends on the other; install
either, both, or neither.

> On `summary`: the reduction covers the whole segment, silence included, and
> slices usually end with some. For descriptors that read 0 in silence — pitch
> especially — a `'mean'` is dragged towards zero in proportion to how quiet the
> tail is. Prefer `'median'` when sorting or matching.

## Building the WebAssembly

Only needed if you're working on the package itself; the published tarball
ships the built modules.

```bash
source /path/to/emsdk/emsdk_env.sh     # Emscripten
npm run build                          # build:wasm + catalog
npm test
```

`FLUID_PATH=/path/to/flucoma-core` reuses an existing checkout instead of
letting CMake fetch one.

The programs are built single-threaded: `FluidCLIWrapper.hpp` runs the job on
the calling thread under Emscripten rather than spawning one, so the modules
need neither `SharedArrayBuffer` nor cross-origin isolation headers and drop
into any page. Native builds are unaffected.

# Minimal Quick Build

Minimal build steps below. For detailed guidance see https://github.com/flucoma/flucoma-cli/wiki/Compiling

## Prerequisites 

* C++14 compliant compiler (clang, GCC or MSVC)
* cmake 
* make (or Ninja or XCode or VisualStudio)
* git 
* an internet connection 

CMake will automatically download the dependencies needed

```bash
mkdir -p build && cd build
cmake ..
make install
```

This will assemble a package in `release-packaging`.

Alternatively, flucoma-cli is now on the [AUR / Arch User Repository](https://aur.archlinux.org/packages/flucoma-cli-git/) and can now be compiled and downloaded by executing:

```bash
yay -S flucoma-cli-git
```

on Arch Linux and Manjaro (with thanks to @madskjeldgaard)
